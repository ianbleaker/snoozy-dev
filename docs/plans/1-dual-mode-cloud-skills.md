# 1 — Make skills dual-mode for CLI and Claude Code cloud

## Context

Source issue: #1

The plugin was designed CLI-only (`gh`, `ssh`, `~/.ssh/config`, `~/development/<project>`) and is now also used in Claude Code cloud sessions, where `gh` is absent, there is no ssh alias or key, and GitHub access is via `mcp__github__*` tools. Found by running `/next-task` in a cloud session, where every `gh` step had to be translated by hand. Goal: every skill works in both modes; **CLI behavior must not regress** (with `gh` on PATH and the cloud env vars unset, every script and skill behaves exactly as today).

Decisions already made (do not re-litigate):

- **Mode detection:** `gh` not on PATH = cloud. Why: the simplest signal that is true in exactly the case that breaks.
- **Branch naming in cloud:** `task/<N>-<slug>` wins for `/next-task` and `/batch-tasks`, overriding the session-assigned `claude/...` branch for task work only; ad hoc work stays on the session branch. Why: `group-branches.sh`, `rebuild-and-deploy.sh`, `merge-preview`, `sweep-tasks` and the In Review derivation all key on `task/<N>-*`; the alternatives touch every one of them.
- **`gh`-dependent helper scripts (hybrid):**
  - `group-branches.sh` and `staged-prs.sh` (real logic) accept pre-fetched JSON so the skill fetches via MCP and the script keeps the logic. With no JSON given they call `gh` as today.
  - `rebuild-and-deploy.sh`, `merge-prs.sh`, `sweep.sh` get a `gh`-missing guard; the skill performs the equivalent MCP steps.
  - Why: no token in the container (rejected: installing `gh` with a PAT secret, broader than the MCP's repo scope) and logic is not re-derived from prose.
- **`deploy`, `stage-preview` and the smoke/sense check are cloud-capable** via environment-secret SSH, with a **dedicated restricted deploy key**, a **preflight first**, and a **CLI-only fallback with a clear error** if outbound SSH (port 22) or preview HTTP is blocked. Why: the VPS accepts SSH from outside and the preview is public plain HTTP; the user's own key is passphrased and root-capable so it must never be used in cloud.
- **Secrets contract** (environment variables only; no values ever in git or docs): `SNOOZY_DEPLOY_HOST`, `SNOOZY_DEPLOY_USER`, `SNOOZY_DEPLOY_SSH_KEY` (PEM text), `SNOOZY_DEPLOY_KNOWN_HOSTS` (the server's host-key line, **required — pinned, never `accept-new`**), optional `SNOOZY_DEPLOY_PORT` (default 22). Why pinned: otherwise a man-in-the-middle captures a root-capable deploy.
- **Shared SSH wrapper** lives in `project-patterns/remote-ssh.sh` (not next to one skill) because both `deploy` and `stage-preview` use it; `project-patterns/` already holds the shared `smoke-driver.mjs`.
- **Server-side gate** is documented and templated only (`project-patterns/deploy-gate.sh` + a section in `deploy-scripts.md`). This plan changes nothing on the server.
- **`onboard` in cloud:** label creation, branch protection and repo settings have no MCP equivalent, so the cloud path prints the exact `gh` commands for the user to run on the CLI.
- **Playwright/Chromium in cloud:** Chromium is preinstalled (`PLAYWRIGHT_BROWSERS_PATH=/opt/pw-browsers`); the project needs `npm ci` if `node_modules` is missing.
- **Unverified (the plan must not assume):** whether the cloud environment's network policy allows outbound SSH on 22 and HTTP to the preview `ip:port`; whether the VPS firewall restricts by source IP. The preflight is how these get answered; failure means CLI-only, not a broken skill.

## Before starting

- Read `CLAUDE.md` (invariants: skills in `plugins/snoozy-dev/skills/<name>/SKILL.md`, helper scripts next to the skill that uses them — the shared ones go in `project-patterns/`; never overwrite a user's existing project config; doc-sync table).
- Read the current versions of every file named below before editing it.
- `scripts/verify.sh` must pass at the start and after every checklist item that touches a `.sh` or `.mjs`.
- Use placeholders (`<host>`, `<user>`, `<alias>`, `<key-path>`, `<preview-port>`) in every doc and comment. Never write a real hostname, IP, username, key or domain.
- For CLI-no-regression checks use a stub `ssh` / `gh` on a temporary `PATH` (in the scratchpad directory) that prints its arguments; do not contact any real host.

## Do not do

- Do not touch the VPS, `authorized_keys`, or any server config; do not attempt SSH or HTTP to any real host.
- Do not write any real hostname, IP, username, domain, key or `known_hosts` line anywhere; placeholders only.
- Do not use, reference or rely on the user's personal SSH key or `~/.ssh/config` alias in cloud mode.
- Do not use `StrictHostKeyChecking accept-new` or `no`; do not make `SNOOZY_DEPLOY_KNOWN_HOSTS` optional.
- Do not install `gh` or add a `GH_TOKEN` path for cloud.
- Do not change CLI behavior: with `gh` on PATH and the `SNOOZY_DEPLOY_*` vars unset, every `ssh`/`gh` call must be byte-identical to today.
- Do not add a non-root deploy user, adopt `subscribe_pr_activity` / `send_later` / Routines, or fix the `deploy-scripts.md` citation paths — all deferred to separate issues.
- Do not add, rename or remove a skill; do not change `scripts/install-plugin.sh`.
- Do not create labels, branch protection or repo settings from a cloud session.
- Do not regenerate or edit this plan doc while implementing; escalate instead.
