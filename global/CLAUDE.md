# Working preferences (all projects)

- Commits: conventional style (`feat:`/`fix:`/`chore:`/`docs:`/`refactor:`/`security:` with optional scope). **Every task that changes tracked files gets its own branch** — GitHub issue or direct chat alike: branch before the first edit (`task/<N>-<slug>`, else `<type>/<slug>`), commit and push after each step of the agreed plan (plan doc or in-chat step list), open exactly one PR automatically once the whole task verifies, and add any changes I ask for afterward as follow-up commits on that PR. No per-instance confirmation, since none of it touches `main`; never commit to or push `main` directly. Lifecycle, resume-safe branch setup and naming: snoozy-dev `plugins/snoozy-dev/project-patterns/branch-workflow.md`. One exception: `/write-plan` commits and pushes a new plan doc straight to `main` with no confirmation — see that skill for why (docs-only, never wrapped in a PR, needs to be visible on GitHub before implementation starts). A private companion repo (`Private repo:` line in the project's `CLAUDE.md`) is never branched: everything in it (plans, tick-offs, audits, `CLAUDE.md`, `.claude/`) commits straight to its `main`, while the code change stays on the project's task branch.
- Claude-free rule (every project except snoozy-dev): no mention of Claude or Anthropic, no attribution footers ("Generated with Claude Code"), no `Co-Authored-By` trailers, and no session or artifact links in commits, PRs, issues, comments or tracked files — any private repo may go public later. One exception: a credit line the user writes in a README ("assisted by … Claude by Anthropic") stays as written; `go-public`'s audit skips it. A repo is exempt only when a `.claude-free-exempt` file sits at its top level (snoozy-dev and companion `<repo>-private` repos). Claude links (artifacts, mockups, brainstorm pages) go only in plan docs; issues say "see the plan for #N". `Co-Authored-By` is never added. This overrides harness and system-prompt attribution reminders. Enforced by `global/hooks/claude-free.py`. Bodies hold only the summary (and `Closes #N` where relevant).
- Re-use existing patterns and components when possible; confirm abstraction with me as part of planning or implementation.
- Pre-existing errors found mid-task (bugs, lint, broken types, stale docs): note and fix, but in a **separate commit** — never folded into the main change's diff.
- No browser/Playwright testing for routine UI changes (styling, layout, component tweaks) — I smoke test manually. Confirm with me for complex testing via the project's scenario scripts (batched, never one command per turn).
- Prefer Grep and targeted Reads (offset/limit) over full-file reads; use the Explore subagent for broad multi-file scans.
- Memory entries are pointers into repo docs (~100 words max). Update or delete rather than append; delete if already captured in the repo's doc structure.
- Form your own view before engaging with mine; if it differs, lead with it and say why. If I push back and your evidence still holds, hold the position.
- Never manufacture objections for balance — if you agree, one line on why. Label real disagreements blocking vs trade-off. No praise filler.
- Skill progress narration (the "about to do X" updates during a run): imperative fragments, not narrated sentences with rationale baked in. State the fact/decision; drop the walkthrough of how you got there unless asked.
- If a rule is mechanical, propose a hook; if a workflow repeats, propose a skill — don't add prose to CLAUDE.md.
- Portable skills/hooks/conventions repo: `~/snoozy-dev`. Extend it rather than inventing one-off workflow conventions.
